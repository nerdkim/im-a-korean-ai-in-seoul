# 설치 전후 예시

README의 설치 전후 비교에 쓴 요청 열두 가지와 받은 답변입니다.

요청 열두 가지를 Claude Opus 5.5에 보냈습니다. 요청마다 이 도구를 설치한 프로젝트에서 두 번, 이 도구가 없는 프로젝트에서 두 번 보냈습니다. 요청을 보낼 때마다 새 세션을 열었습니다.
두 프로젝트는 평가 스크립트가 임시 디렉터리에 새로 만들었습니다. 이 도구가 없는 프로젝트는 빈 디렉터리였습니다. 이 도구를 설치한 프로젝트에도 이 도구 말고는 아무것도 없었습니다. hook과 skill은 이 도구를 설치한 프로젝트에서 실제로 동작했습니다. 두 프로젝트에서 모두 Claude가 쓸 수 있는 Claude Code 도구는 Skill, Read, Bash뿐이었습니다. Claude Code는 사용자 설정과 MCP 서버를 불러오지 않았습니다. Claude Code는 이 평가용으로 새로 만든 설정 디렉터리를 썼습니다.
Claude Code 2.1.310에서 effort를 medium으로 두고 2026년 10월 27일(한국 시간)에 실행했습니다. 요청 원문은 [showcase.json](../test/fixtures/eval/showcase.json)에 있습니다.

요청마다 요청 원문과 두 프로젝트의 첫 번째 답변을 싣습니다. 답변은 Claude가 쓴 글을 그대로 옮겼습니다. 줄마다 앞에 `>`를 붙여 인용으로 표시하고 줄바꿈이 보이도록 줄 끝에 공백을 더한 것 말고는 바꾸지 않았습니다. 두 번째 답변은 싣지 않았습니다. 요청마다 붙인 설명은 두 프로젝트에서 받은 답변 네 개를 모두 읽고 썼습니다.
이번 실행에서는 Stop hook이 다시 쓰라고 요구한 답변이 없었습니다.

설명에는 다음 기준으로 본 것을 적었습니다. 검사기로 센 숫자는 README의 표에 있습니다.

- 머리말: 요청한 글 앞에 붙여 답변 자체를 설명하는 문장
- 덧붙인 말: 요청한 글 뒤에 붙인 제안, 질문, 설명
- 요청에 없는 내용: 연도, 요일, 원인, 테스트 목록, 예시 코드처럼 요청에 없는데 답변에 넣은 사실, 목록, 코드
- 표현: 한국어로 굳은 말 대신 쓴 영어, 같은 뜻을 두 번 쓴 말, 받침과 맞지 않는 조사처럼 [korean-rewrite skill](../skill/korean-rewrite/SKILL.md)이 고치라고 하는 표현
- 내용: 요청에 적힌 사실이 빠진 곳과 기술 설명이나 제품 화면 이름이 틀린 곳

기술 설명은 제품의 공식 문서나 소스 코드와 대조했습니다. Chrome 화면에 나오는 이름은 Chromium 소스 코드와 한국어 번역 파일로 확인했습니다.

## 1. Chrome 확장 프로그램을 고친 뒤 반영되지 않을 때 할 일 묻기

**요청**

<!-- korean-style-quote -->
> Chrome extension을 만들고 있어. Profile 11 프로필에 개발용으로 올려 두고 테스트하는데, 방금 content script랑 manifest를 고쳤는데도 예전 동작 그대로야. 내가 뭘 하면 되는지 짧게 알려 줘.  
<!-- /korean-style-quote -->

**이 도구가 없는 프로젝트의 첫 번째 답변**

<!-- korean-style-quote -->
> Chrome은 파일을 고쳐도 자동으로 다시 읽지 않아요. 아래 순서대로 해 보세요.  
>
> 1. **Profile 11 창에서 확장 다시 로드**  
>    Profile 11로 열린 창의 주소창에 `chrome://extensions`를 입력하고, 확장 카드의 새로고침(↻) 버튼을 누르세요. `manifest.json`을 고쳤다면 이 단계가 꼭 필요해요. 다른 프로필 창에서 누르면 적용되지 않아요.  
>
> 2. **테스트하던 웹페이지 새로고침**  
>    이미 열려 있던 탭에는 예전 content script가 그대로 남아 있어요. 확장을 다시 로드한 뒤 해당 탭도 F5로 새로고침해야 새 스크립트가 들어가요.  
>
> 그래도 예전처럼 동작하면 아래를 확인해 보세요.  
>
> - **로드된 폴더가 맞는지**: 확장 카드의 "세부정보"에서 소스 경로를 보세요. 빌드 도구를 쓰고 있다면 `src`가 아니라 `dist` 같은 빌드 결과 폴더가 로드되어 있을 수 있어요. 그 경우 다시 빌드하거나 watch 모드를 켜 두세요.  
> - **오류 표시**: 카드에 빨간 "오류" 버튼이 있으면 manifest 파싱 실패 같은 문제로 새 버전이 적용되지 않은 거예요. 오류 내용을 확인하세요.  
> - **그래도 안 되면**: 확장을 삭제하고 "압축해제된 확장 프로그램 로드"로 다시 올려 보세요.  
<!-- /korean-style-quote -->

**이 도구를 설치한 프로젝트의 첫 번째 답변**

<!-- korean-style-quote -->
> Chrome의 Profile 11에서 확장 프로그램을 새로고침한 뒤 테스트할 탭도 새로고침해야 합니다.  
>
> 1. Profile 11 창에서 `chrome://extensions`를 열고 해당 확장 프로그램 카드의 새로고침 아이콘을 눌러 주십시오. manifest를 고쳤다면 이 단계를 꼭 거쳐야 반영됩니다.  
> 2. 테스트하던 탭을 새로고침해 주십시오. 이미 열려 있던 탭에는 예전 content script가 남아 있습니다. 확장 프로그램을 새로고침해도 이 탭에는 새 스크립트가 자동으로 들어가지 않습니다.  
>
> 이렇게 해도 그대로라면 다음 두 가지를 확인해 주십시오.  
>
> - 카드에 `오류` 버튼이 보이면 manifest를 읽지 못한 것입니다. 이때 Chrome은 고친 내용을 반영하지 않습니다.  
> - 카드에 나오는 로드 경로가 실제로 고친 폴더와 같아야 합니다. 번들러를 쓴다면 빌드 결과물이 그 폴더에 새로 생성됐는지도 확인해 주십시오.  
<!-- /korean-style-quote -->

**프로젝트마다 두 번 받은 답변에서 본 것**

- 이 도구가 없는 프로젝트에서 Claude는 두 번 모두 해요체로만 답했고 첫 문장 다음에 `아래 순서대로 해 보세요.`나 `순서대로 해 보세요.`라는 머리말을 넣었습니다. 두 번 모두 Chrome 화면의 "확장 프로그램"을 대부분 `확장`으로 줄여 썼고 카드의 새로고침 버튼을 누르는 일을 `다시 로드`라고도 불렀습니다. 두 번 모두 마지막 항목에서는 확장 프로그램을 삭제한 뒤 다시 로드하는 방법까지 권했습니다.
- 이 도구를 설치한 프로젝트에서 Claude는 두 번 모두 합니다체로만 답했고 Chrome 화면에 나오는 `확장 프로그램`과 `새로고침`이라는 말을 썼습니다. 두 번째 답변은 `Chrome의 Profile 11에서 다음 순서로 해 주십시오.`라는 머리말로 시작했고 확장 프로그램을 새로고침하는 일을 `다시 로드`라고도 불렀습니다. 두 번 모두 확인할 것 두 가지로 답을 끝냈고 확장 프로그램을 삭제하라고 권하지는 않았습니다.
- 두 프로젝트에서 모두 Claude는 두 번 다 확장 프로그램을 먼저 새로고침한 뒤 테스트하던 탭을 새로고침하라고 순서를 맞게 알려 주었습니다. emoji, 가운뎃점, 줄표, 생성 표시를 넣은 답변은 없었습니다. 한국어 Chrome에서는 로드한 폴더의 경로가 카드에 나오지 않습니다. "세부정보"를 눌러야 "출처" 항목에 "로드 위치:"로 나옵니다. 이 도구가 없는 프로젝트에서 Claude는 두 번 모두 이 경로를 "세부정보"에서 보라고 맞게 안내했습니다. 다만 첫 번째 답변에서는 이 경로를 한국어 Chrome 화면에 없는 `소스 경로`라는 말로 불렀습니다. 설치한 프로젝트에서 Claude는 두 번 모두 경로가 카드에 나온다고 잘못 안내했습니다. 첫 번째 답변에서는 `카드에 나오는 로드 경로가`, 두 번째 답변에서는 `카드에 표시된 로드 경로가`라고 썼습니다.

## 3. 영어 README 문단을 한국어로 옮기기

**요청**

<!-- korean-style-quote -->
> 다음 README 문단을 한국어로 옮겨 줘. 설명은 붙이지 마.  
>
> This tool allows you to run the same checks locally that our CI runs. Make sure Docker is running before you start. Results are written to the reports directory, and a summary is printed once all checks have completed. If a check fails, the exit code is set to 1 so that it can be used in pre-commit hooks.  
<!-- /korean-style-quote -->

**이 도구가 없는 프로젝트의 첫 번째 답변**

<!-- korean-style-quote -->
> 이 도구를 사용하면 CI에서 실행하는 것과 동일한 검사를 로컬에서 실행할 수 있습니다. 시작하기 전에 Docker가 실행 중인지 확인하세요. 결과는 reports 디렉터리에 저장되며, 모든 검사가 완료되면 요약이 출력됩니다. 검사가 실패하면 종료 코드가 1로 설정되므로 pre-commit 훅에서 활용할 수 있습니다.  
<!-- /korean-style-quote -->

**이 도구를 설치한 프로젝트의 첫 번째 답변**

<!-- korean-style-quote -->
> 이 도구를 쓰면 CI에서 돌리는 검사를 로컬에서 똑같이 돌릴 수 있습니다. 시작하기 전에 Docker가 실행 중인지 확인해 주십시오. 결과는 reports 디렉터리에 기록됩니다. 모든 검사가 끝나면 요약을 출력합니다. 검사가 하나라도 실패하면 종료 코드가 1이 되므로 pre-commit hook에서 쓸 수 있습니다.  
<!-- /korean-style-quote -->

**프로젝트마다 두 번 받은 답변에서 본 것**

- 이 도구가 없는 프로젝트에서 받은 두 답변은 `저장되며`와 `기록되며` 한 낱말만 달랐습니다. Claude는 두 번 모두 합니다체 문장 사이에 해요체 `확인하세요`를 섞었고 hook을 소리 나는 대로 `pre-commit 훅`이라고 적었습니다. 원문 `a summary is printed`와 `the exit code is set to 1`은 수동태와 낱말을 그대로 따라 `요약이 출력됩니다`, `종료 코드가 1로 설정되므로`라고 옮겼습니다.
- 이 도구를 설치한 프로젝트에서 Claude는 두 번 모두 합니다체로만 썼고 hook을 `pre-commit hook`이라고 영어로 적었습니다. `the exit code is set to 1`은 두 번 모두 `종료 코드가 1이 되므로`라고 풀어 옮겼습니다. `a summary is printed`는 첫 번째 답변에서 `요약을 출력합니다`로 바꿨지만 두 번째 답변에서는 원문 수동태를 따라 `요약이 출력됩니다`라고 옮겼습니다.
- 두 프로젝트의 답변 네 개에는 모두 머리말이나 덧붙인 말 없이 옮긴 문단만 있었습니다. 원문 네 문장의 뜻을 틀리게 옮긴 곳은 어느 답변에도 없었고 원문에 없는 내용이나 emoji, 가운뎃점, 줄표도 없었습니다. 네 답변 모두 `allows you to`를 `이 도구를 사용하면`이나 `이 도구를 쓰면`으로 시작하는 문장으로 풀었습니다. 다만 네 답변 모두 `Results are written`을 `저장되며`, `기록되며`, `기록됩니다`, `저장되고`로 옮겨 원문 수동태를 그대로 따랐습니다.

**요청**

<!-- korean-style-quote -->
> 배포하고 나서 결제 API가 가끔 502를 내. 어디부터 보면 돼?  
<!-- /korean-style-quote -->

**이 도구가 없는 프로젝트의 첫 번째 답변**

<!-- korean-style-quote -->
> 작업 디렉터리가 비어 있어서 코드나 설정은 못 봤습니다. 그래서 일반적인 순서로 안내할게요. 배포 직후에 502가 "가끔" 나면 원인은 대개 몇 가지 안으로 좁혀집니다.  
>
> ## 1. 502를 누가 냈는지 먼저 확인하기  
> 502는 앱이 아니라 앞단 프록시(LB, Nginx, Ingress, API Gateway)가 "업스트림한테서 제대로 된 응답을 못 받았다"고 알리는 코드입니다.  
> - **LB/프록시 로그**에서 502가 찍힌 요청의 업스트림 상태, 응답 시간, 에러 사유를 보세요.  
>   - Nginx: `upstream prematurely closed connection`, `connect() failed`, `no live upstreams`  
>   - AWS ALB: `elb_status_code=502`인데 `target_status_code`가 `-`이면 앱이 응답하기 전에 연결이 끊긴 겁니다.  
> - 같은 시각 **앱 로그에 그 요청이 아예 없다면** 앱까지 도달하지 못한 거라 인프라 쪽 문제입니다. **있다면** 앱 쪽 문제입니다.  
>
> ## 2. 가장 흔한 원인 (확률 높은 순)  
> 1. **keep-alive 타임아웃 불일치**: 간헐적 502의 대표 원인입니다. 앱 서버의 keep-alive 타임아웃이 LB의 idle timeout보다 짧으면, LB가 이미 닫힌 커넥션을 재사용하다가 502가 납니다.  
>    - 앱의 keep-alive를 LB보다 길게 잡으세요. 예: ALB 60s면 앱은 65s.  
>    - Node.js는 `server.keepAliveTimeout` 기본값이 5s라서 특히 자주 걸립니다.  
> 2. **배포 중 graceful shutdown/롤링 문제**: 502가 배포 시점에만 몰려 있다면 이쪽입니다.  
>    - 종료되는 파드나 인스턴스가 처리 중인 요청을 끊어버리는 경우: SIGTERM 처리, `preStop` sleep, LB deregistration delay를 확인하세요.  
>    - 아직 준비가 안 된 인스턴스로 트래픽이 들어가는 경우: readiness probe나 헬스체크가 너무 일찍 통과하지 않는지 보세요.  
> 3. **프로세스 크래시/OOM 재시작**: `kubectl describe pod`에서 `OOMKilled`가 있는지, restart count가 늘고 있는지 확인하세요.  
> 4. **결제 PG 등 외부 호출 지연**: PG 응답이 느려서 프록시 타임아웃(`proxy_read_timeout`, Gateway 타임아웃)을 넘기는 경우입니다. 504로 나오는 게 보통이지만 구성에 따라 502로 보일 수 있습니다.  
> 5. **이번 배포의 변경점**: 커넥션 풀 크기, 워커 수, 리소스 limit, 런타임이나 라이브러리 버전, 환경변수(PG 엔드포인트나 인증서)가 바뀌었는지 보세요.  
>
> ## 3. 시간 분포로 좁히기  
> - **배포 시각에만 몰림** → 2번(graceful shutdown/readiness)  
> - **배포 후 계속, 트래픽이 적을 때 더 자주** → 1번(keep-alive)  
> - **트래픽 피크에 몰림** → 리소스, 풀 고갈, 타임아웃  
> - **특정 인스턴스에만 몰림** → 그 노드나 파드 문제  
>
> ## 4. 결제 API라서 꼭 확인할 것  
> 502는 클라이언트가 응답을 못 받았다는 뜻이지, **실제 결제가 실패했다는 뜻이 아닙니다.** 클라이언트가 재시도하면 이중 결제가 날 수 있으니, 502가 난 요청의 실제 PG 처리 결과를 대조해보고 멱등성 키를 쓰고 있는지 확인하세요.

>
> 1. **프록시 로그에서 502가 난 요청의 원인 메시지를 확인합니다.** Nginx라면 error.log에 `upstream prematurely closed connection`, `connect() failed (111: Connection refused)`, `no live upstreams` 가운데 무엇이 찍혔는지 봅니다. >
> 2. **502가 난 시각을 배포 시각, 인스턴스 재시작 시각과 맞춰 봅니다.** 배포 직후 몇 분 동안만 502가 몰린다면 롤링 업데이트 중에 종료되는 인스턴스로 요청이 갔을 가능성이 큽니다. 이때는 다음 세 가지를 확인해 주십시오.  
>    - readiness probe가 앱이 실제로 요청을 받을 수 있을 때만 통과하는지 확인합니다.  
>    - 앱이 종료 신호를 받은 뒤에도 처리 중인 요청을 끝까지 마치는지(graceful shutdown) 확인합니다.  
>    - 프록시 대상에서 빠지기 전에 프로세스가 먼저 종료되지 않도록 preStop 대기 시간을 두었는지 확인합니다.  
>
> 3. **배포와 상관없이 드문드문 계속 난다면 keep-alive 타임아웃을 의심합니다.** 앱 서버의 keep-alive 타임아웃이 프록시의 유휴 타임아웃보다 짧으면 문제가 생깁니다. 앱이 이미 닫은 연결을 프록시가 다시 쓰려다 502를 냅니다. Node.js의 기본값은 5초이고 ALB 유휴 타임아웃의 기본값은 60초라서 이 조합에서 자주 생깁니다. 앱 쪽 값을 프록시보다 길게 잡아야 합니다.  
>
> 4. **인스턴스 재시작 횟수와 OOMKilled 기록을 확인합니다.** 이번 배포 뒤로 메모리 사용량이 늘어 프로세스가 죽었다가 다시 뜨면, 그 사이에 들어온 요청이 502가 됩니다.  
>
> 5. **이번 배포의 diff를 확인합니다.** 런타임 버전, 서버 설정(타임아웃, 워커 수), 의존성이 바뀌었는지 봅니다. 결제 API가 외부 PG를 호출한다면 응답 시간이 길기 때문에 타임아웃 설정이 바뀐 영향을 먼저 받습니다.

- 이 도구가 없는 프로젝트에서 Claude는 두 번 모두 커밋 메시지 본문을 `제한한다`와 `반환한다`처럼 해라체로 썼고 코드 블록 뒤에 해요체 문장을 덧붙였습니다. 첫 번째 답변은 `영문 버전이 필요하면 아래를 쓰면 돼요.`라며 영어 커밋 메시지를 하나 더 덧붙였습니다. 두 번째 답변은 본문에 메모에 없는 도입 이유 `무차별 대입 공격을 막기 위해`를 넣었습니다. 덧붙인 문단에서는 이 이유가 짐작이라고 밝히고 Conventional Commits 형식의 제목도 권했습니다. 같은 답변의 본문은 rate limit과 429 반환을 문장으로 한 번 쓰고 목록으로 한 번 더 썼습니다.
- 이 도구를 설치한 프로젝트에서 Claude는 두 번 모두 `feat: 로그인 API에 rate limit 추가`라는 제목과 합니다체 본문 세 문장만 코드 블록에 담았습니다. 앞뒤에 아무 말도 붙이지 않았고 메모에 없는 내용도 넣지 않았습니다.
- 두 프로젝트의 답변 네 개에는 모두 메모의 세 가지가 빠짐없이 들어 있었습니다. 커밋 메시지에 생성 표시를 넣은 답변은 없었습니다.

## 10. 함수에 한국어 주석 달기

**요청**

<!-- korean-style-quote -->
> 아래 함수에 한국어 주석을 달아 줘. 코드는 바꾸지 마.  
>
> ```js
> function backoffDelay(attempt, base = 200, max = 10000) {
>   const delay = Math.min(max, base * 2 ** attempt);
>   return delay / 2 + Math.random() * (delay / 2);
> }
> ```
<!-- /korean-style-quote -->

**이 도구가 없는 프로젝트의 첫 번째 답변**

<!-- korean-style-quote -->
> ```js
> /**
>  * 지수 백오프(exponential backoff)에 지터(jitter)를 적용해 재시도 대기 시간을 계산한다.
>  *
>  * @param {number} attempt - 재시도 횟수 (0부터 시작)
>  * @param {number} [base=200] - 기본 대기 시간(ms)
>  * @param {number} [max=10000] - 대기 시간 상한(ms)
>  * @returns {number} 대기 시간(ms). delay/2 이상 delay 미만의 값
>  */
> function backoffDelay(attempt, base = 200, max = 10000) {
>   // 시도할 때마다 대기 시간을 두 배로 늘리되 max를 넘지 않게 한다.
>   const delay = Math.min(max, base * 2 ** attempt);
>   // 절반은 고정하고 나머지 절반은 무작위로 정한다(equal jitter).
>   // 여러 클라이언트가 같은 시점에 동시에 재시도하는 것을 막는다.
>   return delay / 2 + Math.random() * (delay / 2);
> }
> ```
>
> 코드는 바꾸지 않고 주석만 추가했습니다. 반환값은 지터를 적용하기 전 `delay`의 50% 이상 100% 미만입니다. 예를 들어 `attempt = 3`이면 `delay`는 1600ms이고, 실제 대기 시간은 800ms 이상 1600ms 미만입니다.  
<!-- /korean-style-quote -->

**이 도구를 설치한 프로젝트의 첫 번째 답변**

<!-- korean-style-quote -->
> ```js
> /**
>  * 재시도할 때 기다릴 시간을 지수 백오프로 계산합니다.
>  * 반환값의 단위는 base, max와 같습니다.
>  *
>  * @param {number} attempt 몇 번째 재시도인지 나타냅니다. 0이면 기다리는 시간이 base입니다.
>  * @param {number} base 처음 기다릴 시간입니다.
>  * @param {number} max 기다리는 시간의 상한입니다.
>  * @returns {number} delay/2 이상 delay 미만의 무작위 값입니다.
>  */
> function backoffDelay(attempt, base = 200, max = 10000) {
>   // 재시도할 때마다 기다리는 시간을 두 배로 늘리고, max를 넘지 않게 자릅니다.
>   const delay = Math.min(max, base * 2 ** attempt);
>   // 절반은 고정하고 나머지 절반은 무작위로 정합니다.
>   // 여러 클라이언트가 같은 시각에 한꺼번에 다시 요청하지 않게 하려는 것입니다.
>   return delay / 2 + Math.random() * (delay / 2);
> }
> ```
<!-- /korean-style-quote -->

**프로젝트마다 두 번 받은 답변에서 본 것**

- 이 도구가 없는 프로젝트에서 Claude는 두 번 모두 주석을 `계산한다`처럼 해라체로 달고 코드 블록 뒤 설명은 `미만입니다`와 `기다립니다`처럼 합니다체로 썼습니다. 그래서 한 답변 안에서 문장 끝이 바뀌었습니다. 두 번 모두 주석에 `지수 백오프(exponential backoff)`, `지터(jitter)`처럼 같은 뜻의 영어를 괄호로 덧붙였습니다. 코드 블록 뒤에는 두 번 모두 `attempt` 값에 따라 기다리는 시간을 예로 든 설명을 붙였습니다. 첫 번째 답변은 이 설명 앞에 `코드는 바꾸지 않고 주석만 추가했습니다.`라는 문장도 넣었습니다. 같은 답변의 주석 `같은 시점에 동시에 재시도하는`은 같은 뜻을 두 번 썼습니다.
- 이 도구를 설치한 프로젝트에서 Claude는 두 번 모두 주석을 합니다체로만 달았고 코드 블록 밖에는 아무 말도 붙이지 않았습니다. 첫 번째 답변에서는 `attempt` 설명에 `0이면 기다리는 시간이 base입니다.`, `base` 설명에 `처음 기다릴 시간입니다.`라고 썼습니다. 하지만 `attempt`가 0일 때 기다리는 시간은 `base`의 절반 이상 `base` 미만입니다. 이 두 설명은 같은 답변의 `@returns`와도 어긋납니다.
- 두 프로젝트의 답변 네 개는 모두 코드를 바꾸지 않았습니다. 네 답변 모두 대기 시간이 시도마다 두 배로 늘다가 `max`에서 멈춘다는 점과 돌려주는 값이 `delay`의 절반 이상 `delay` 미만이라는 점을 코드와 맞게 적었습니다. 이 도구가 없는 프로젝트의 두 답변과 설치한 프로젝트의 두 번째 답변에는 코드에 없는 밀리초 단위 `(ms)`가 붙어 있었습니다. 설치한 프로젝트의 첫 번째 답변은 단위를 정하지 않고 `반환값의 단위는 base, max와 같습니다.`라고 적었습니다. 설치한 프로젝트의 두 번째 답변을 뺀 세 답변에서는 연결 어미 뒤에 빼도 뜻이 같은 쉼표를 찍었습니다.

## 11. 쿠버네티스 Pod가 Pending인 이유 묻기

**요청**

<!-- korean-style-quote -->
> 쿠버네티스에 새로 배포한 Pod가 계속 Pending이고, 이벤트에 0/3 nodes are available: 3 Insufficient cpu라고 나와. 노드 CPU 사용률은 30%밖에 안 되는데 왜 이래?  
<!-- /korean-style-quote -->

**이 도구가 없는 프로젝트의 첫 번째 답변**

<!-- korean-style-quote -->
> 원인은 **스케줄러가 실제 CPU 사용률이 아니라 `requests` 합계를 기준으로 판단하기 때문**입니다.  
>
> ## 왜 이런 일이 생기나  
>
> kube-scheduler는 Pod를 배치할 때 이 조건만 확인합니다.  
>
> ```
> 노드 Allocatable CPU − (노드에 있는 모든 Pod의 CPU requests 합) ≥ 새 Pod의 CPU requests
> ```
>
> 실제 사용량(`kubectl top`, 모니터링 대시보드의 30%)은 계산에 들어가지 않습니다. 기존 Pod들이 requests를 넉넉하게 잡아두고 실제로는 적게 쓰면, 사용률이 30%여도 **예약 기준으로는 노드가 꽉 찬 상태**가 됩니다.  
>
> ## 확인 방법  
>
> **1. 노드별 requests 할당 현황 보기**  
> ```bash
> kubectl describe node <노드명> | grep -A 10 "Allocated resources"
> ```
> ```
> Resource  Requests      Limits
> cpu       3850m (96%)   6 (150%)   ← 여기가 문제
> ```
> 여기 `Requests` 비율이 90% 이상이면 이게 원인입니다.  
>
> **2. 새 Pod가 요청하는 CPU 값 확인**  
> ```bash
> kubectl get pod <pod명> -o jsonpath='{.spec.containers[*].resources}'
> ```
> initContainer가 있으면 그 requests도 계산에 들어갑니다. 실수로 `cpu: "2"`를 `2000m` 대신 `20`처럼 너무 크게 넣지 않았는지도 확인해 보세요.  
>
> **3. requests를 많이 잡고 있는 Pod 찾기**  
> ```bash
> kubectl get pods -A -o custom-columns=NS:.metadata.namespace,NAME:.metadata.name,NODE:.spec.nodeName,CPU_REQ:.spec.containers[*].resources.requests.cpu
> ```
> DaemonSet(로깅, 모니터링, CNI 에이전트 등)이 노드마다 생각보다 많이 차지하는 경우도 흔합니다.  
>
> ## 해결 방법  
>
> | 방법 | 설명 |  
> |---|---|  
> | **새 Pod의 requests 낮추기** | 실제로 필요한 만큼만 요청하도록 조정 |  
> | **기존 Pod requests 현실화** | `kubectl top pod`나 VPA 추천값을 보고 과하게 잡힌 requests를 줄이기. 효과가 가장 크고 근본적인 해결책입니다 |  
> | **LimitRange 기본값 확인** | requests를 명시하지 않았는데 namespace의 LimitRange가 큰 기본값을 넣고 있을 수 있음: `kubectl get limitrange -n <ns> -o yaml` |  
> | **노드 추가 / Cluster Autoscaler** | requests가 실제로 필요한 수준이면 용량을 늘려야 함 |  
> | **Pending 상태의 다른 Pod 정리** | 끝난 Job, 안 쓰는 Deployment replica 등 |  
>
> ## 참고  
> - 메시지가 `3 Insufficient cpu`만 나오면 taint, affinity, 메모리 문제는 아니고 순수하게 CPU requests 부족입니다.  
> - requests를 너무 낮추면 노드에 Pod가 과하게 몰려 실제 부하가 걸릴 때 CPU throttling이나 성능 저하가 생길 수 있습니다. 실측 사용량의 p95 정도를 기준으로 잡는 것을 권장합니다.  
>
> `kubectl describe node` 결과의 `Allocated resources` 부분과 Pod의 resources 설정을 보여주시면 구체적으로 어디를 줄이면 될지 같이 봐드릴게요.  
<!-- /korean-style-quote -->

**이 도구를 설치한 프로젝트의 첫 번째 답변**

<!-- korean-style-quote -->
> 스케줄러는 실제 CPU 사용률이 아니라 각 Pod가 선언한 `resources.requests.cpu` 합계를 보고 노드를 고릅니다. 실제 사용률이 30%여도 노드에 이미 올라간 Pod들의 requests 합계가 노드의 allocatable CPU에 가까우면, 새 Pod의 requests가 들어갈 자리가 없어 `Insufficient cpu`로 Pending 상태가 됩니다.  
>
> 다음 순서로 확인해 주십시오.  
>
> ```bash
> # 노드별 requests 합계와 allocatable 비교
> kubectl describe node <노드이름> | grep -A 8 "Allocated resources"
>
> # 새 Pod가 요청한 CPU 확인
> kubectl get pod <pod이름> -o jsonpath='{.spec.containers[*].resources}'
> ```
>
> `Allocated resources`의 CPU Requests가 90% 넘게 차 있고 새 Pod의 requests가 남은 양보다 크면 이 경우에 해당합니다. 자주 보는 원인은 다음과 같습니다.  
>
> - 기존 Pod들의 requests가 실제 사용량보다 크게 잡혀 있습니다. 실제 사용량은 `kubectl top pod`로 비교할 수 있습니다.  
> - 새 Pod의 requests가 지나치게 큽니다. 예를 들어 `cpu: "2"`를 요청했는데 노드마다 남은 양이 1코어씩뿐이면, 클러스터 전체로는 여유가 있어도 어느 노드에도 올라가지 못합니다.  
> - 네임스페이스의 LimitRange가 requests 기본값을 크게 넣고 있습니다. `kubectl get limitrange -n <네임스페이스>`로 확인할 수 있습니다.  
> - allocatable은 노드 전체 코어 수보다 작습니다. kubelet과 시스템 예약분(`kube-reserved`, `system-reserved`)을 뺀 값이기 때문입니다.  
>
> 해결 방법은 세 가지입니다. 기존 Pod와 새 Pod의 requests를 실제 사용량에 맞게 줄이거나, 노드를 추가하거나, Cluster Autoscaler를 설정해 노드가 자동으로 늘어나게 할 수 있습니다. requests를 줄일 때는 limits와 따로 생각해야 합니다. requests는 스케줄링 기준이고 limits는 실행 중 상한입니다.  
<!-- /korean-style-quote -->

**프로젝트마다 두 번 받은 답변에서 본 것**

- 이 도구가 없는 프로젝트에서 Claude는 두 번 모두 합니다체 사이에 `확인해 보세요` 같은 해요체를 섞었습니다. 두 번 모두 `kubectl describe node` 결과를 보여 주면 같이 보겠다고 제안하며 답변을 끝냈습니다. 두 번 모두 요청에 없던 `3850m (96%)` 출력을 예라는 표시 없이 지어 넣었습니다. 첫 번째 답변은 해결 방법 표에 `Pending 상태의 다른 Pod 정리`를 넣고 그 예로 `끝난 Job`을 들었습니다. 하지만 스케줄러는 아직 노드에 배치되지 않은 Pending Pod와 실행을 마친 Pod의 requests를 세지 않습니다. 그래서 이런 Pod를 정리해도 노드에 자리가 생기지 않습니다.
- 이 도구를 설치한 프로젝트에서 Claude는 두 번 모두 합니다체로만 썼고 출력을 지어 넣거나 제안을 붙이지 않았습니다. 첫 번째 답변에서는 `가까우면,`과 `1코어씩뿐이면,`처럼 연결 어미 뒤에 쉼표를 찍었습니다.
- 두 프로젝트에서 모두 Claude는 두 번 다 스케줄러가 실제 사용률이 아니라 requests 합계를 보고 Pod를 배치한다고 맞게 설명했습니다. 네 답변 모두 머리말 없이 원인으로 시작했고 `kubectl describe node`의 `Allocated resources`에서 requests 비율을 보라고 했습니다. LimitRange 기본값을 확인하라는 내용도 네 답변에 모두 있었습니다.

## skill 예문과 겹치는 요청

요청 열두 가지 가운데 1, 3, 4, 7, 12번 요청은 skill 예문과 같은 낱말이나 문장을 씁니다. 그래서 요청을 이 다섯 가지와 나머지 일곱 가지로 나눴습니다. 그리고 이 문서 앞에 적은 기준 가운데 머리말, 덧붙인 말, 요청에 없는 내용 세 가지를 사람이 답변을 읽고 셌습니다. 한 답변에 같은 항목이 여러 번 나와도 한 번으로 셌습니다. 머리말은 답변의 첫 문단에서 답변 자체를 소개하거나 이어질 순서를 알리는 문장만 셌습니다. 요청에 없는 내용은 요청한 글이나 답 안에 넣은 것만 셌습니다. 요청한 글이나 답 뒤에 덧붙인 말 안에 든 내용은 덧붙인 말로만 셌습니다. 질문에 답하는 1, 6, 11번 요청에서는 답변에 쓴 설명과 확인 방법을 요청에 없는 내용으로 세지 않았습니다. 이 세 요청에서는 지어 넣은 명령 출력과 질문에 없던 주제를 다룬 절만 셌습니다. 답변마다 무엇을 셌는지는 위 요청별 설명에 있습니다.

| 항목 | 겹치는 요청, 이 도구가 없는 프로젝트 | 겹치는 요청, 이 도구를 설치한 프로젝트 | 겹치지 않는 요청, 이 도구가 없는 프로젝트 | 겹치지 않는 요청, 이 도구를 설치한 프로젝트 |
| --- | --- | --- | --- | --- |
| 머리말이 있는 답변 | 10개 중 4개 | 10개 중 1개 | 14개 중 4개 | 14개 중 1개 |
| 덧붙인 말이 있는 답변 | 10개 중 3개 | 10개 중 1개 | 14개 중 11개 | 14개 중 2개 |
| 요청에 없는 내용이 있는 답변 | 10개 중 4개 | 10개 중 0개 | 14개 중 11개 | 14개 중 1개 |

skill 예문과 겹치지 않는 요청에서도 머리말, 덧붙인 말, 요청에 없는 내용은 이 도구를 설치한 프로젝트의 답변에서 더 적게 나왔습니다. 그러므로 이 차이는 skill 예문과 겹치는 요청에서만 나타난 것이 아닙니다. 다만 korean-rewrite skill의 `AI가 자주 쓰는 습관` 절은 머리말을 붙이거나 말을 덧붙이거나 요청에 없는 내용을 넣는 일을 어떤 글에서든 하지 말라고 합니다. 이 절은 `테스트 목록`, `예시 코드`, `코드를 붙여 주시면 다시 써 드릴게요` 같은 예도 듭니다. 5번 PR 설명과 8번 리뷰 코멘트에서 센 내용은 이 예와 거의 같습니다. 그리고 5번 PR 설명, 8번 리뷰 코멘트, 9번 커밋 메시지는 skill의 글 종류별 관례가 다루는 글입니다. 그래서 겹치지 않는 요청에서 나온 차이도 skill의 다른 지시와 예 때문일 수 있습니다. 두 묶음의 요청이 다섯 가지와 일곱 가지뿐이므로 묶음에 따라 차이의 크기가 다른지는 이 숫자로 말할 수 없습니다.

어떤 낱말을 골랐는지는 두 묶음으로 나눠 비교하지 못했습니다. 겹치는 요청에서 두 프로젝트의 답변이 다르게 쓴 skill 예문의 낱말은 1번 요청의 `확장 프로그램`과 3번 요청의 `hook`입니다. 이 도구를 설치한 프로젝트의 답변은 두 낱말을 skill 예문대로 썼고 이 도구가 없는 프로젝트의 답변은 1번 요청에서 `확장 프로그램`을 대부분 `확장`으로 줄여 썼고 3번 요청에서는 `훅`이라고 썼습니다. 이 차이는 skill 예문 때문일 수 있습니다.

## 다시 실행하기

아래 명령으로 같은 비교를 다시 할 수 있습니다. 앞의 두 명령은 유료 API를 호출합니다. 마지막 명령은 저장한 결과만 세므로 API를 호출하지 않습니다. 같은 요청이어도 답변은 실행할 때마다 달라질 수 있습니다. 비용과 시간도 캐시와 서버 상태에 따라 달라집니다.

```bash
npm run eval -- --run --cases test/fixtures/eval/showcase.json --models claude-opus-5-5 --effort medium --repeat 2 --individual --with-hooks --profiles baseline --out .eval/baseline
npm run eval -- --run --cases test/fixtures/eval/showcase.json --models claude-opus-5-5 --effort medium --repeat 2 --individual --with-hooks --profiles installed --out .eval/installed
npm run eval -- --summary .eval/baseline .eval/installed
```

`--with-hooks`를 주면 두 프로젝트에서 모두 Claude가 Skill, Read, Bash를 쓸 수 있습니다. hook과 skill은 이 도구를 설치한 프로젝트에서 실제로 동작합니다. `--with-hooks`를 빼면 실행 조건이 이 문서와 달라집니다. 이때 평가 스크립트는 `--profiles installed`로 만든 프로젝트에도 이 도구를 설치하지 않고 작성 지침만 넣습니다. Claude는 두 프로젝트에서 모두 아무 도구도 쓸 수 없습니다.
`--individual`을 주면 요청마다 새 세션을 엽니다. 이 옵션을 빼면 평가 스크립트는 요청을 모두 묶어 한 번에 보냅니다. `--effort`를 주지 않으면 `low`로 실행합니다. 결과는 `--out`에 준 경로에 저장합니다. 이미 결과가 있는 경로를 주면 실행하지 않고 멈춥니다. 이 저장소에서는 결과를 `.eval/` 아래에만 두고 커밋하지 않습니다.
`--cases`로 다른 평가 입력을 고를 수 있습니다. 이 옵션을 주지 않으면 평가 스크립트는 `cases.json`을 씁니다. 평가 입력은 [test/fixtures/eval/](../test/fixtures/eval/)에 있습니다. `calque.json`은 한국어로 옮기면 영어식 표현이 나오기 쉬운 영어 문장을 모은 입력입니다. 번역 요청이 아닌 질문도 하나 들어 있습니다. 이 질문은 답변에 영어를 낱말 단위로 옮겨 만든 말이 나오는지 보려고 넣었습니다. 평가 스크립트는 요청마다 `mustNot`에 적은 표현이 답변에 나오면 제약 위반으로 셉니다.
이 문서의 결과는 이 평가용으로 새로 만든 설정 디렉터리로 앞의 두 명령을 실행해 얻었습니다. 사용자 설정 디렉터리에 든 내용이 요청에 섞이지 않도록 `CLAUDE_CONFIG_DIR` 환경 변수로 설정 디렉터리를 따로 정했습니다. 새로 만든 설정 디렉터리로 처음 실행했을 때는 시스템 프롬프트가 다음 실행과 달랐습니다. Claude Code가 서버의 기능 설정을 아직 받지 못했기 때문으로 보입니다. 그래서 평가하기 전에 `claude -p`를 두 번 실행해 기능 설정을 받아 두었습니다.
`--summary`는 같은 요청을 다시 보낸 결과가 있으면 비용을 처음 보낸 요청과 다시 보낸 요청으로 나눠 보여 줍니다. 같은 요청을 다시 보내면 API가 처음 요청 때 캐시에 저장해 둔 입력을 다시 읽으므로 비용이 줄어듭니다. 두 비용의 차이가 작으면 평가 도중 Claude Code의 시스템 프롬프트가 바뀌어 캐시를 쓰지 못했을 수 있습니다. 같은 날 먼저 실행한 평가에서는 이 도구를 설치한 프로젝트에 같은 요청을 다시 보내는 도중 시스템 프롬프트가 바뀐 것으로 보입니다. 다시 보낸 세 번째 요청부터는 처음 보낼 때 저장한 입력을 캐시에서 읽지 못했습니다. 네 번째 요청부터 캐시에서 읽은 앞부분은 처음 보낸 요청보다 81토큰 짧았습니다. 그래서 다시 보낸 요청의 평균 비용이 0.109달러로 처음 보낸 요청의 0.124달러보다 조금밖에 줄지 않았습니다.
