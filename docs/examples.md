# 설치 전후 예시

README의 설치 전후 비교에 쓴 요청 열두 가지와 받은 답변입니다.

요청 열두 가지를 Claude Opus 5.5에 보냈습니다. 요청마다 이 도구를 설치한 프로젝트에서 두 번, 이 도구가 없는 프로젝트에서 두 번 보냈습니다. 요청을 보낼 때마다 새 세션을 열었습니다.
두 프로젝트는 평가 스크립트가 임시 디렉터리에 새로 만들었습니다. 이 도구가 없는 프로젝트는 빈 디렉터리였습니다. 이 도구를 설치한 프로젝트에도 이 도구 말고는 아무것도 없었습니다. hook과 skill은 이 도구를 설치한 프로젝트에서 실제로 동작했습니다. 두 프로젝트에서 모두 Claude가 쓸 수 있는 Claude Code 도구는 Skill, Read, Bash뿐이었습니다. Claude Code는 사용자 설정과 MCP 서버를 불러오지 않았습니다.
Claude Code 2.1.302에서 effort를 medium으로 두고 2026년 10월 18일(한국 시간)에 실행했습니다. 요청 원문은 [showcase.json](../test/fixtures/eval/showcase.json)에 있습니다.

요청마다 요청 원문과 두 프로젝트의 첫 번째 답변을 싣습니다. 답변은 Claude가 쓴 글을 그대로 옮겼습니다. 줄마다 앞에 `>`를 붙여 인용으로 표시하고 줄바꿈이 보이도록 줄 끝에 공백을 더한 것 말고는 바꾸지 않았습니다. 두 번째 답변은 싣지 않았습니다. 요청마다 붙인 설명은 두 프로젝트에서 받은 답변 네 개를 모두 읽고 썼습니다.
이번 실행에서는 Stop hook이 다시 쓰라고 요청한 답변이 없었습니다.

설명에는 다음 기준으로 본 것을 적었습니다. 검사기로 센 숫자는 README의 표에 있습니다.

- 머리말: 요청한 글 앞에 붙여 답변 자체를 설명하는 문장
- 덧붙인 말: 요청한 글 뒤에 붙인 제안, 질문, 설명
- 요청에 없는 내용: 연도, 요일, 원인, 테스트 목록, 예시 코드처럼 요청에 없는데 답변에 넣은 사실, 목록, 코드
- 표현: 한국어로 굳은 말 대신 쓴 영어, 같은 뜻을 두 번 쓴 말, 받침과 맞지 않는 조사처럼 [korean-rewrite skill](../skill/korean-rewrite/SKILL.md)이 고치라고 하는 표현
- 내용: 요청에 적힌 사실이 빠진 곳과 기술 설명이나 제품 화면 이름이 틀린 곳

## 1. Chrome 확장 프로그램을 고친 뒤 반영되지 않을 때 할 일 묻기

**요청**

<!-- korean-style-quote -->
> Chrome extension을 만들고 있어. Profile 11 프로필에 개발용으로 올려 두고 테스트하는데, 방금 content script랑 manifest를 고쳤는데도 예전 동작 그대로야. 내가 뭘 하면 되는지 짧게 알려 줘.  
<!-- /korean-style-quote -->

**이 도구가 없는 프로젝트의 첫 번째 답변**

<!-- korean-style-quote -->
> Profile 11 창에서 다음 순서로 해 보세요.  
>
> 1. **확장 다시 로드**: `chrome://extensions`에서 해당 확장 카드의 새로고침(↻) 버튼을 누릅니다. 압축 해제된 확장은 파일을 고쳐도 자동으로 반영되지 않습니다. manifest를 바꿨다면 이 단계가 꼭 필요합니다.  
> 2. **테스트 중인 탭 새로고침**: content script는 이미 열려 있는 탭에 다시 주입되지 않습니다. 확장을 다시 로드한 뒤 대상 페이지를 새로고침하세요. 그래도 그대로면 탭을 닫고 새로 여세요.  
> 3. **로드된 경로 확인**: 카드의 "세부정보"에서 소스 경로가 지금 수정한 폴더와 같은지 봅니다. 빌드 도구를 쓴다면 `dist` 같은 출력 폴더를 다시 빌드했는지도 확인하세요.  
> 4. **오류 확인**: 카드에 "오류" 버튼이 보이면 눌러 보세요. manifest에 오류가 있으면 새 버전을 불러오지 못하고 예전 상태가 남을 수 있습니다.  
> 5. **그래도 안 되면**: 확장을 삭제하고 "압축해제된 확장 프로그램을 로드합니다"로 다시 올리세요. manifest의 `matches`, `permissions`, `host_permissions`를 바꿨을 때 가끔 필요합니다.  
>
> 대부분은 1번과 2번을 하면 해결됩니다.  
<!-- /korean-style-quote -->

**이 도구를 설치한 프로젝트의 첫 번째 답변**

<!-- korean-style-quote -->
> 1. Profile 11 창에서 `chrome://extensions`를 열고, 해당 확장 프로그램 카드의 새로고침 아이콘을 눌러 주십시오. manifest를 고쳤다면 이렇게 확장 프로그램을 새로고침해야 반영됩니다.  
> 2. 테스트하던 웹 페이지도 새로고침해 주십시오. 이미 열려 있던 탭에는 예전 content script가 그대로 남아 있습니다.  
>
> 그래도 예전 동작이 나오면 두 가지를 확인해 주십시오.  
>
> - 카드에 `오류` 버튼이 보이면 눌러 내용을 확인해 주십시오. manifest에 오류가 있으면 수정한 내용이 반영되지 않습니다.  
> - 카드의 소스 경로가 지금 수정하고 있는 폴더와 같은지 확인해 주십시오. 빌드 결과물 폴더(예: `dist`)를 로드했다면 다시 빌드해야 수정한 내용이 들어갑니다.  
<!-- /korean-style-quote -->

**프로젝트마다 두 번 받은 답변에서 본 것**

- 이 도구가 없는 프로젝트에서 Claude는 두 번 모두 `해 보세요`로 끝나는 해요체 머리말로 답을 시작했고 합니다체 본문에도 `확인하세요` 같은 해요체를 섞었습니다. 두 번 모두 Chrome 화면의 "확장 프로그램"을 `확장`으로 줄여 썼고 카드의 `새로고침(↻) 버튼`을 누르라고 하면서 같은 일을 `다시 로드`라고도 불렀습니다. 마지막 줄에는 앞 단계를 다시 가리키는 문장을 덧붙였습니다. 첫 번째 답변에서는 `대부분은 1번과 2번을 하면 해결됩니다.`, 두 번째 답변에서는 `보통은 2번과 3번만 하면 해결됩니다.`라고 썼습니다.
- 이 도구를 설치한 프로젝트에서 Claude는 두 번 모두 끝에 덧붙인 말 없이 합니다체로만 답했고 Chrome 화면에 나오는 `확장 프로그램`과 `새로고침`이라는 말을 썼습니다. 두 번째 답변만 `Chrome에서는 파일을 고친 뒤 확장 프로그램과 탭을 둘 다 새로고침해야 바뀐 코드가 적용됩니다.`라는 문장으로 시작했습니다. 이 문장은 뒤의 두 단계를 미리 요약합니다. 다만 두 번 모두 로드한 폴더의 경로를 카드에서 찾게 했습니다. 첫 번째 답변에서는 `카드의 소스 경로가`, 두 번째 답변에서는 `카드에 나오는 로드 경로가`라고 썼습니다.
- 두 프로젝트에서 모두 Claude는 두 번 다 순서를 맞게 알려 주었습니다. 확장 프로그램을 먼저 새로고침한 뒤 테스트하던 탭을 새로고침하라고 했습니다. emoji, 가운뎃점, 줄표, 생성 표시를 넣은 답변도 없었습니다. 한국어 Chrome에서는 로드한 폴더의 경로가 카드에 나오지 않습니다. "세부정보"를 눌러야 "출처" 항목에 "로드 위치:"로 나옵니다. 이 도구가 없는 프로젝트에서는 두 번 모두 이 경로를 "세부정보"에서 보라고 맞게 안내했습니다. 하지만 이 도구가 없는 프로젝트의 두 번째 답변에서는 "출처" 항목을 `"소스"`라고 적었습니다. 두 프로젝트의 첫 번째 답변에서는 모두 이 경로를 한국어 Chrome 화면에 없는 `소스 경로`라는 말로 불렀습니다.

## 3. 영어 README 문단을 한국어로 옮기기

**요청**

<!-- korean-style-quote -->
> 다음 README 문단을 한국어로 옮겨 줘. 설명은 붙이지 마.  
>
> This tool allows you to run the same checks locally that our CI runs. Make sure Docker is running before you start. Results are written to the reports directory, and a summary is printed once all checks have completed. If a check fails, the exit code is set to 1 so that it can be used in pre-commit hooks.

**이 도구가 없는 프로젝트의 첫 번째 답변**

<!-- /korean-style-quote -->

**이 도구를 설치한 프로젝트의 첫 번째 답변**

<!-- korean-style-quote -->
> 이 도구를 쓰면 CI에서 돌리는 검사를 로컬에서도 똑같이 실행할 수 있습니다. 시작하기 전에 Docker가 실행 중인지 확인해 주십시오. 결과는 `reports` 디렉터리에 저장됩니다. 모든 검사가 끝나면 요약을 출력합니다. 검사가 하나라도 실패하면 종료 코드를 1로 설정하므로 pre-commit hook에서 쓸 수 있습니다.  
<!-- /korean-style-quote -->

**프로젝트마다 두 번 받은 답변에서 본 것**

- 이 도구가 없는 프로젝트에서 받은 두 답변은 서로 글자 하나 다르지 않았습니다. Claude는 두 번 모두 합니다체 문장 사이에 해요체 `확인하세요`를 섞었고 hook을 소리 나는 대로 `pre-commit 훅`이라고 적었습니다. 원문 `a summary is printed`와 `the exit code is set to 1`은 수동태와 낱말을 그대로 따라 `요약이 출력됩니다`, `종료 코드가 1로 설정되므로`라고 옮겼습니다.
- 이 도구를 설치한 프로젝트에서 Claude는 두 번 모두 합니다체로만 썼고 hook을 `pre-commit hook`이라고 영어로 적었습니다. 첫 번째 답변의 `종료 코드를 1로 설정하므로`는 수동태를 능동으로 바꾼 구절이지만 주어가 없습니다. 그래서 같은 문장 끝의 `쓸 수 있습니다`처럼 사용자가 하는 일로 읽힐 수 있습니다. 두 번째 답변에서는 `the exit code is set to 1`을 `종료 코드가 1이 되므로`라고 풀어 옮겼지만 `a summary is printed`는 원문 수동태와 낱말을 그대로 따라 `요약이 출력됩니다`라고 옮겼습니다.
- 두 프로젝트의 답변 네 개에는 모두 머리말이나 덧붙인 말 없이 옮긴 문단만 있었습니다. 원문 네 문장의 뜻을 틀리게 옮긴 곳은 어느 답변에도 없었고 원문에 없는 내용이나 emoji, 가운뎃점, 줄표도 없었습니다. 다만 네 답변 모두에서 `Results are written`을 `저장되며`나 `저장됩니다`로 옮겨 원문 수동태를 그대로 따랐습니다.

## 6. 배포 뒤 502가 날 때 어디부터 볼지 묻기

**요청**

<!-- korean-style-quote -->
> 배포하고 나서 결제 API가 가끔 502를 내. 어디부터 보면 돼?  
<!-- /korean-style-quote -->

**이 도구가 없는 프로젝트의 첫 번째 답변**

<!-- korean-style-quote -->
> 작업 디렉터리가 비어 있어서 코드나 설정은 확인하지 못했습니다. 그래서 일반적인 순서로만 정리해 드립니다.  
>
> 502는 앞단 프록시나 로드밸런서가 **뒤쪽 앱에서 정상 응답을 받지 못했다**는 뜻입니다. 그래서 "앱이 무엇을 반환했나"보다 "프록시와 앱 사이 연결이 왜 끊겼나"를 먼저 봐야 합니다.  
>
> ## 1. 502가 언제 몰리는지 확인 (가장 먼저)  
> - **배포하는 동안이나 직후에만 몰리는지** 아니면 **배포 후 계속 가끔 나는지** 확인하세요. 이 둘은 원인이 완전히 다릅니다.  
> - 로드밸런서(ALB/nginx/Ingress) 액세스 로그에서 502 요청의 시각, 처리한 타깃(파드나 인스턴스), 응답 시간을 뽑아 보세요.  
>   - 특정 인스턴스에만 몰리면 그 인스턴스 문제입니다.  
>   - 응답 시간이 0ms에 가까우면 연결이 바로 거부되거나 리셋된 것입니다.  
>   - 응답 시간이 길면 타임아웃 쪽입니다.  
>
> ## 2. 배포 중에만 난다면: 롤링 배포 처리  
> - **readiness probe**: 앱이 준비되기 전에 트래픽을 받고 있지 않은지 보세요.  
> - **graceful shutdown**: SIGTERM을 받으면 처리 중인 요청을 마치고 종료하는지 보세요. k8s라면 `preStop`에 `sleep 5~15`를 넣어서 엔드포인트에서 빠질 시간을 줘야 합니다. 또 `terminationGracePeriodSeconds`가 가장 긴 결제 요청 시간보다 길어야 합니다.  
> - **LB deregistration delay / connection draining** 설정도 확인하세요.  
>
> ## 3. 배포 후 계속 가끔 난다면: keep-alive 타임아웃 불일치 (제일 흔함)  
> - **앱 서버의 keep-alive 타임아웃이 LB의 idle timeout보다 짧으면** LB가 이미 닫힌 연결을 재사용하다가 502가 납니다.  
>   - 예: ALB의 기본값은 60초, Node.js의 `keepAliveTimeout` 기본값은 5초입니다.  
>   - 해결: 앱 쪽을 LB보다 길게 잡으세요 (Node라면 `keepAliveTimeout=65s`, `headersTimeout`은 그보다 조금 더 길게).  
> - 이번 배포에서 런타임, 프레임워크, 베이스 이미지가 바뀌었다면 이 기본값이 함께 바뀌었을 수 있습니다.  
>
> ## 4. 앱 프로세스가 죽거나 재시작되는지  
> - 파드나 컨테이너의 재시작 횟수, OOMKilled, 크래시 로그를 확인하세요 (`kubectl get pods`, `kubectl describe pod`).  
> - 이번 배포로 메모리 사용량이 늘었는지도 보세요.  
>
> ## 5. 결제 API에만 해당하는 부분  
> - **외부 PG 호출 타임아웃이 프록시 타임아웃보다 길면** 프록시가 먼저 끊고 502나 504를 냅니다. PG 타임아웃 < 앱 타임아웃 < 프록시 타임아웃 순서가 되도록 맞추세요.  
> - PG 쪽 커넥션 풀이 고갈되거나 PG 응답이 느려지면 워커가 모자라서 502가 날 수 있습니다.  
> - ⚠️ 결제는 **재시도할 때 중복 결제 위험**이 있습니다. 502를 받은 요청이 실제로 PG에서 승인됐는지 따로 확인하고, idempotency key를 쓰고 있는지도 점검하세요.  
>

> 먼저 502를 누가 냈는지 확인해야 합니다. 502는 앞단(로드 밸런서, Ingress, Nginx)이 뒤쪽 앱에서 정상 응답을 받지 못했을 때 내는 코드입니다. 그래서 앱 로그보다 프록시 로그가 먼저입니다.  
>
> **1. 프록시 로그에서 502가 난 요청을 찾습니다**  
>
> Nginx라면 `error.log`에 이유가 남습니다. 메시지에 따라 볼 곳이 다릅니다.  
>
> | 메시지 | 의심할 원인 |  
> |---|---|  
> | `upstream prematurely closed connection` | 앱이 keep-alive 연결을 먼저 끊었습니다 |  
> | `connect() failed (111: Connection refused)` | 아직 뜨지 않았거나 이미 내려간 인스턴스로 요청이 갔습니다 |  
> | `no live upstreams` | 대상 인스턴스가 모두 비정상으로 표시됐습니다 |  
>
> AWS ALB라면 액세스 로그의 `elb_status_code`와 `target_status_code`를 같이 봅니다. `target_status_code`가 `-`이면 앱까지 요청이 가지 못했거나 앱이 응답 없이 연결을 끊은 것입니다.  
>
> **2. 502가 난 시각을 배포 시각과 맞춰 봅니다**  
>
> 배포 직후 몇 분 동안만 몰려 있으면 롤링 배포에서 생기는 문제일 가능성이 큽니다. 다음 세 가지를 확인해 주십시오.  
>
> - readiness probe가 실제로 요청을 받을 준비가 됐을 때만 성공하는지 확인합니다.  
> - 종료할 때 `SIGTERM`을 받고 처리 중인 요청을 마친 뒤 내려가는지 확인합니다. Kubernetes라면 `preStop`에 몇 초 `sleep`을 넣어 엔드포인트에서 먼저 빠지게 해야 합니다.  
> - 로드 밸런서의 deregistration delay(연결 드레이닝 시간)가 충분한지 확인합니다.  
>
> **3. 배포와 상관없이 드문드문 난다면 keep-alive 타임아웃을 봅니다**  
>
> 앱 서버의 keep-alive 타임아웃이 로드 밸런서의 idle timeout보다 짧으면, 앱이 막 닫은 연결로 로드 밸런서가 요청을 보내 502가 납니다. 예를 들어 ALB 기본값은 60초이고 Node.js `server.keepAliveTimeout` 기본값은 5초입니다. 이 경우 앱 쪽 값을 로드 밸런서보다 길게 잡아야 합니다. 이번 배포에서 런타임, 프레임워크 버전, 서버 설정이 바뀌었다면 이 값도 같이 바뀌었을 수 있습니다.  
>
> **4. 앱 인스턴스가 재시작했는지 봅니다**  
>
> `kubectl get pods`의 `RESTARTS` 수, OOMKilled 이벤트, 메모리 그래프를 확인합니다. 이번 배포로 메모리 사용량이 늘어 인스턴스가 죽고 있다면 그때마다 502가 납니다.  
>
> 로그 메시지나 인프라 구성(Kubernetes, ALB, Nginx 등)을 알려 주시면 범위를 더 좁힐 수 있습니다.  
<!-- /korean-style-quote -->

**프로젝트마다 두 번 받은 답변에서 본 것**

- 이 도구가 없는 프로젝트에서 Claude는 두 번 모두 머리말에서 `작업 디렉터리가 비어 있어서` 코드나 설정을 보지 못했다고 밝혔습니다. 두 번 모두 요청에 없던 항목을 `⚠️`와 함께 넣어 502가 난 결제가 PG에서 승인됐는지 확인하라고 당부했습니다. 두 번 모두 합니다체 사이에 `확인하세요` 같은 해요체를 섞었습니다. 두 번째 답변에는 `정리할게요`, `나와요`, `나나요`, `드릴게요` 같은 해요체와 가운뎃점이 더 있습니다. 첫 번째 답변에는 Claude에게 없는 경험을 내세운 `경험상`이 있고 두 번째 답변에는 목적어와 서술어가 맞지 않는 `앱을 65초 정도로 올리고`가 있습니다.
- 이 도구를 설치한 프로젝트에서 Claude는 두 번 모두 머리말 없이 `먼저 502를 누가 냈는지`로 답을 시작했고 처음부터 끝까지 합니다체로 썼습니다. 두 번 모두 emoji나 가운뎃점을 쓰지 않았고 502가 난 결제가 PG에서 승인됐는지 확인하라고 당부하지도 않았습니다. 두 번째 답변에서는 로드 밸런서 설정인 deregistration delay를 낱말마다 옮겨 `대상 등록 해제 대기 시간`이라고 썼습니다. 같은 답변의 `워커가 끊기면서`는 주어와 서술어가 맞지 않습니다.
- 두 프로젝트에서 모두 Claude는 답변마다 끝에 요청에 없는 부탁을 덧붙였습니다. 로그나 인프라 구성을 알려 달라는 부탁입니다. 이 도구가 없는 프로젝트에서는 알려 주면 직접 확인하거나 원인을 좁혀 주겠다고 했습니다. 설치한 프로젝트에서는 알려 주면 원인을 더 좁힐 수 있다고 했습니다. 네 답변 모두에서 `타임아웃`과 `timeout`을 섞어 썼고 `멱등키(idempotency key)`나 `deregistration delay(연결 드레이닝 시간)`처럼 같은 뜻을 두 번 쓰기도 했습니다. 틀린 기술 설명은 네 답변 어디에도 없었습니다.

> - Limit login requests to 10 per minute per IP
> - Return 429 Too Many Requests when the limit is exceeded
> - Add tests for rate limiting behavior
> ```
<!-- /korean-style-quote -->

**이 도구를 설치한 프로젝트의 첫 번째 답변**

## 10. 함수에 한국어 주석 달기

**요청**

<!-- korean-style-quote -->
> 아래 함수에 한국어 주석을 달아 줘. 코드는 바꾸지 마.  
>
> ```js
> function backoffDelay(attempt, base = 200, max = 10000) {
>   const delay = Math.min(max, base * 2 ** attempt);
>   return delay / 2 + Math.random() * (delay / 2);
> }
> ```
<!-- /korean-style-quote -->

**이 도구가 없는 프로젝트의 첫 번째 답변**

<!-- korean-style-quote -->
> ```js
> /**
>  * 재시도 횟수에 따라 지수 백오프(exponential backoff) 대기 시간을 계산한다.
>  * 여러 클라이언트가 동시에 재시도하지 않도록 무작위 지터(jitter)를 섞는다.
>  *
>  * @param {number} attempt - 재시도 횟수 (0부터 시작)
>  * @param {number} [base=200] - 기본 대기 시간(ms)
>  * @param {number} [max=10000] - 대기 시간 상한(ms)
>  * @returns {number} 실제로 기다릴 시간(ms)
>  */
> function backoffDelay(attempt, base = 200, max = 10000) {
>   // 재시도할 때마다 대기 시간을 두 배로 늘리되 max를 넘지 않게 한다.
>   const delay = Math.min(max, base * 2 ** attempt);
>   // 계산한 값의 절반은 그대로 두고, 나머지 절반 범위에서 무작위 값을 더한다.
>   // 결과는 [delay/2, delay) 범위에 들어간다.
>   return delay / 2 + Math.random() * (delay / 2);
> }
> ```
>
> 예를 들어 `attempt`가 0이면 100~200ms, 3이면 800~1600ms를 기다립니다. `attempt`가 6 이상이면 계산값이 10000ms 상한에 걸려서 대기 시간은 5000~10000ms가 됩니다. 코드는 바꾸지 않았고 주석만 달았습니다.  
<!-- /korean-style-quote -->

**이 도구를 설치한 프로젝트의 첫 번째 답변**

<!-- korean-style-quote -->
> ```js
> /**
>  * 재시도 전에 기다릴 시간을 지수 백오프로 계산하고 지터를 더해 돌려줍니다.
>  *
>  * @param {number} attempt 몇 번째 재시도인지 나타냅니다. 값이 1 늘 때마다 기본 대기 시간이 두 배가 됩니다.
>  * @param {number} [base=200] attempt가 0일 때의 기본 대기 시간입니다.
>  * @param {number} [max=10000] 기본 대기 시간의 상한입니다.
>  * @returns {number} delay/2 이상 delay 미만인 대기 시간입니다. 단위는 base, max와 같습니다.
>  */
> function backoffDelay(attempt, base = 200, max = 10000) {
>   // base에 2^attempt를 곱해 대기 시간을 늘리되 max를 넘지 않게 합니다.
>   const delay = Math.min(max, base * 2 ** attempt);
>   // 절반은 고정하고 나머지 절반만 무작위로 정합니다.
>   // 여러 클라이언트가 같은 시각에 한꺼번에 재시도하지 않게 하려는 것입니다.
>   return delay / 2 + Math.random() * (delay / 2);
> }
> ```
<!-- /korean-style-quote -->

**프로젝트마다 두 번 받은 답변에서 본 것**

- 이 도구가 없는 프로젝트에서 Claude는 두 번 모두 주석을 `계산한다`처럼 해라체로 달고 코드 블록 뒤 설명은 `됩니다`처럼 합니다체로 썼습니다. 그래서 한 답변 안에서 문장 끝이 바뀌었습니다. 두 번 모두 주석에 `지터(jitter)`처럼 같은 뜻의 영어를 괄호로 덧붙였습니다. 두 번째 답변에서는 `동시에 재시도하는 요청들이 한꺼번에`처럼 뜻이 겹치는 말도 함께 썼습니다. 코드 블록 뒤에는 두 번 모두 `attempt` 값에 따라 기다리는 시간을 예로 든 설명을 붙였습니다. 첫 번째 답변에서는 이 설명 끝에 `코드는 바꾸지 않았고 주석만 달았습니다.`라는 문장도 더했습니다.
- 이 도구를 설치한 프로젝트에서 Claude는 두 번 모두 주석을 합니다체로만 달았고 코드 블록 밖에는 아무 말도 붙이지 않았습니다. 두 번 모두 주석에 `같은 시각에 한꺼번에`처럼 뜻이 겹치는 말을 함께 썼습니다. 두 번째 답변에서 함수 설명에 쓴 `나머지 절반에 무작위 값을 더합니다`는 글자대로 읽으면 계산한 대기 시간보다 길게 기다린다는 뜻입니다. 이 문장은 코드와 맞지 않고 같은 답변의 `@returns`와도 어긋납니다.
- 두 프로젝트의 답변 네 개에는 모두 다음 두 가지가 코드와 맞게 적혀 있었습니다. 대기 시간이 두 배로 늘다가 `max`에서 멈춘다는 점과 돌려주는 값이 `delay`의 절반 이상 `delay` 미만이라는 점입니다. 이 도구가 없는 프로젝트의 두 답변과 설치한 프로젝트의 두 번째 답변에서는 연결 어미 뒤에 `그대로 두고,`나 `늘리고,`처럼 빼도 뜻이 같은 쉼표를 찍었습니다. 이 세 답변에는 코드에 없는 밀리초 단위 `(ms)`도 붙어 있었습니다. 설치한 프로젝트의 첫 번째 답변에서는 단위를 정하지 않고 `단위는 base, max와 같습니다.`라고 적었습니다.

## 11. 쿠버네티스 Pod가 Pending인 이유 묻기

**요청**

<!-- korean-style-quote -->
> 쿠버네티스에 새로 배포한 Pod가 계속 Pending이고, 이벤트에 0/3 nodes are available: 3 Insufficient cpu라고 나와. 노드 CPU 사용률은 30%밖에 안 되는데 왜 이래?  
<!-- /korean-style-quote -->

**이 도구가 없는 프로젝트의 첫 번째 답변**

<!-- korean-style-quote -->
> 스케줄러는 실제 CPU 사용률을 보지 않습니다. Pod들이 선언한 `resources.requests` 합계만 보고 배치를 결정합니다. 그래서 노드 실사용률이 30%여도 이미 떠 있는 Pod들의 requests 합이 노드 Allocatable에 거의 닿아 있으면, 새 Pod의 request가 들어갈 자리가 없다고 판단해 `Insufficient cpu`를 띄웁니다.  
>
> ## 확인 방법  
>
> **1. 노드별 requests 합계 보기**  
> ```bash
> kubectl describe nodes | grep -A 8 "Allocated resources"
> ```
> 출력 예시:  
> ```
>   Resource  Requests      Limits
>   cpu       3800m (95%)   6 (150%)
> ```
> 여기서 Requests가 90% 이상이면 이 상황이 맞습니다. 실사용률은 `kubectl top nodes`로 보는데, 이 값과 비교하면 차이가 보일 겁니다.  
>
> **2. 새 Pod가 요청한 CPU 확인**  
> ```bash
> kubectl get pod <pod-name> -o jsonpath='{.spec.containers[*].resources}'
> ```
> request를 `2`(2코어)처럼 크게 잡았으면 남은 공간 어디에도 안 들어갈 수 있습니다.  
>
> **3. requests를 많이 잡은 Pod 찾기**  
> ```bash
> kubectl get pods -A -o custom-columns=NS:.metadata.namespace,NAME:.metadata.name,CPU_REQ:.spec.containers[*].resources.requests.cpu --sort-by=.metadata.namespace
> ```
>
> ## 자주 보는 원인  
> - **기존 Pod들의 requests가 과하게 잡혀 있음**: 실제로는 100m를 쓰는데 1코어를 요청한 경우가 흔합니다.  
> - **LimitRange가 기본 request를 자동으로 넣음**: requests를 안 적어도 namespace의 LimitRange 기본값이 붙습니다. `kubectl get limitrange -A`로 확인하세요.  
> - **DaemonSet과 시스템 Pod가 차지하는 몫**: 노드마다 kube-proxy, CNI, 로깅·모니터링 에이전트가 requests를 잡고 있습니다.  
> - **Allocatable이 Capacity보다 작음**: kube-reserved와 system-reserved만큼 빠지기 때문에 4코어 노드라도 실제로 쓸 수 있는 건 3.5코어 정도일 수 있습니다.  
>
> ## 해결 방법  
> 1. **새 Pod의 CPU request 줄이기**: 실제 사용량에 맞춰 조정합니다. 예를 들어 `requests.cpu: 250m`처럼요.  
> 2. **기존 워크로드 requests 정리**: `kubectl top pods -A`로 실사용량과 비교해서 과하게 잡힌 걸 줄입니다. VPA를 recommendation 모드로 돌리면 적정값을 추천받을 수 있습니다.  
> 3. **불필요한 Pod나 replica 축소**  
> 4. **노드 추가**: Cluster Autoscaler나 Karpenter를 쓰고 있다면 Pending Pod를 보고 자동으로 노드를 늘려야 합니다. 안 늘어난다면 오토스케일러 로그나 최대 노드 수 제한을 확인하세요.  
>
> 참고로 limits는 스케줄링에 영향을 주지 않고 requests만 봅니다. `describe nodes` 결과를 붙여주시면 어디서 막혔는지 더 구체적으로 봐드릴게요.  
<!-- /korean-style-quote -->

**이 도구를 설치한 프로젝트의 첫 번째 답변**

<!-- korean-style-quote -->
> 스케줄러는 실제 CPU 사용률을 보지 않습니다. 노드의 할당 가능한 CPU(`Allocatable`)에서 이미 배치된 Pod들의 `requests` 합계를 뺀 나머지만 봅니다. 그래서 실제 사용률이 30%여도 다른 Pod들이 CPU를 넉넉하게 요청해 두었다면 새 Pod의 `requests`가 들어갈 자리가 없습니다.  
>
> ## 확인 방법  
>
> 노드마다 요청량이 얼마나 잡혀 있는지 봅니다.  
>
> ```bash
> kubectl describe node <노드이름> | grep -A 10 "Allocated resources"
> ```
>
> 출력의 `cpu Requests` 비율이 100%에 가깝다면 이 경우에 해당합니다. 그다음 새 Pod가 CPU를 얼마나 요청하는지 확인합니다.  
>
> ```bash
> kubectl get pod <pod이름> -o jsonpath='{.spec.containers[*].resources}'
> ```
>
> init 컨테이너가 있으면 그 `requests`도 계산에 들어가므로 함께 확인해 주십시오. 실제 사용량과 비교하려면 `kubectl top pods -A`를 실행합니다. 이 명령은 metrics-server가 있어야 동작합니다.  
>
> ## 흔한 원인  
>
> - 새 Pod의 `requests.cpu`가 노드 하나의 남은 여유보다 큽니다. 클러스터 전체의 여유를 합치면 충분해도 Pod 하나는 노드 하나에만 들어가므로 배치되지 않습니다.  
> - 기존 Pod들이 실제로 쓰는 양보다 `requests`를 훨씬 크게 잡아 두었습니다.  
> - 네임스페이스의 `LimitRange`가 `requests`를 적지 않은 컨테이너에 큰 기본값을 넣습니다. `kubectl get limitrange -n <네임스페이스>`로 확인할 수 있습니다.  
> - DaemonSet과 시스템 Pod가 노드마다 CPU 요청량을 생각보다 많이 차지합니다.  
>
> ## 해결 방법  
>
> 1. 새 Pod의 `requests.cpu`를 실제 사용량에 맞게 낮춥니다.  
> 2. `kubectl top`으로 본 사용량을 기준으로 기존 워크로드의 과한 `requests`를 줄입니다.  
> 3. 요청량이 정말 그만큼 필요하다면 노드를 늘리거나 더 큰 노드를 씁니다. Cluster Autoscaler를 쓰고 있다면 노드 그룹의 최대 개수에 걸렸는지도 확인해 주십시오.  
>
> 위 명령으로 노드별 `cpu Requests` 비율과 새 Pod의 `requests` 값을 보면 이 중 어느 경우인지 가릴 수 있습니다.  
<!-- /korean-style-quote -->

**프로젝트마다 두 번 받은 답변에서 본 것**

- 이 도구가 없는 프로젝트에서 Claude는 두 번 모두 합니다체 사이에 `확인하세요`와 `봐드릴게요` 같은 해요체를 섞었고 명령 결과를 보여 주면 구체적으로 봐 주겠다는 제안으로 답변을 끝냈습니다. 두 번 모두 요청에 없던 `3800m (95%)` 출력을 지어 넣었습니다. 두 번째 답변에서는 이 출력에 예시라는 표시도 붙이지 않았습니다. 두 번 모두 VPA 설정에 없는 이름인 `recommendation 모드`를 썼습니다. 첫 번째 답변에서는 `로깅`과 `모니터링` 사이에 가운뎃점을 넣었습니다.
- 이 도구를 설치한 프로젝트에서 Claude는 두 번 모두 합니다체로만 썼고 출력을 지어 넣거나 제안을 붙이지 않았습니다. 다만 두 번 모두 할당 가능한 양을 우리말로 쓴 뒤 괄호에 같은 뜻의 `Allocatable`을 덧붙였습니다. 두 번째 답변에서는 예약분을 두고 `노드가 작을수록 이 차이가 큽니다`라고 썼습니다. 하지만 노드가 작다고 예약분의 양이 커지지는 않습니다. 노드가 작을수록 예약분이 노드에서 차지하는 비율이 커질 뿐입니다. 같은 답변에서는 새 Pod의 requests도 `kubectl top pod`로 본 사용량에 맞게 줄이라고 권했습니다. 하지만 Pending인 새 Pod는 아직 실행되지 않아 이 명령에 나오지 않습니다.
- 두 프로젝트에서 모두 Claude는 두 번 다 스케줄러가 실제 사용률이 아니라 requests 합계를 보고 Pod를 배치한다고 맞게 설명했습니다. 네 답변 모두 머리말 없이 원인으로 시작했습니다.

## 12. 이용자에게 보낼 점검 공지 쓰기

**프로젝트마다 두 번 받은 답변에서 본 것**

- 이 도구가 없는 프로젝트에서 Claude는 두 번 모두 합니다체 공지에 해요체를 섞었습니다. 첫 번째 답변에서는 `이용해 주세요`, 두 번째 답변에서는 `다시 시도해 주세요`라고 썼습니다. 두 번 모두 공지 뒤에는 `[서비스명]` 같은 빈칸을 채우라는 안내를 덧붙였습니다. 두 번 모두 요청에 없는 연도와 요일을 넣어 날짜를 `2026년 10월 24일(토)`로 적었습니다. 점검 이유도 `더 안정적인 결제 서비스`를 위해서라고 상투적으로 붙였습니다. 첫 번째 답변에서는 결제를 `오전 1시 50분 전까지` 마치라는 마감 시각을 지어 넣었습니다. 두 번째 답변에서는 요청에 없던 결제 취소와 환불 요청을 `중단되는 기능` 항목에 넣으면서 가운뎃점을 썼습니다.
- 이 도구를 설치한 프로젝트에서 Claude는 두 번 모두 합니다체로만 썼고 요청에 없는 연도, 요일, 점검 이유, 빈칸을 넣지 않았습니다. 두 번 모두 공지 뒤에 아무 말도 덧붙이지 않았고 가운뎃점도 쓰지 않았습니다. Claude는 두 번 모두 korean-rewrite skill만 부르고 검사기는 실행하지 않은 채 답변을 썼습니다. Stop hook도 다시 쓰라고 요구하지 않아 처음 쓴 답변이 그대로 나갔습니다.
- 두 프로젝트에서 모두 Claude는 답변마다 점검 날짜와 시간을 적고 결제는 멈추지만 조회는 계속 쓸 수 있다고 밝혔습니다. 네 답변 모두에 요청에 없는 `이용에 불편을 드려 죄송합니다`라는 사과 문장도 들어 있었습니다. 다만 이 도구가 없는 프로젝트의 두 번째 답변에서는 쓸 수 있는 기능을 `조회 기능(주문 내역, 결제 내역 등)과 결제를 제외한 모든 기능`이라고 적었습니다. 이렇게 쓰면 조회도 쓸 수 없다는 뜻으로 읽힐 수 있습니다. 두 프로젝트의 첫 번째 답변에서는 쓸 수 있는 기능을 본문과 목록에서 서로 다른 이름으로 불렀습니다. Claude는 두 답변의 본문에 모두 `다른 기능`이라고 썼습니다. 목록에는 이 도구가 없는 프로젝트에서 `결제 외 모든 기능`이라고, 설치한 프로젝트에서 `나머지 기능`이라고 썼습니다.

## 다시 실행하기

아래 명령으로 같은 비교를 다시 할 수 있습니다. 앞의 두 명령은 유료 API를 호출합니다. 마지막 명령은 저장한 결과만 세므로 API를 호출하지 않습니다. 같은 요청이어도 답변은 실행할 때마다 달라질 수 있습니다. 비용과 시간도 캐시와 서버 상태에 따라 달라집니다.

```bash
npm run eval -- --run --cases test/fixtures/eval/showcase.json --models claude-opus-5-5 --effort medium --repeat 2 --individual --with-hooks --profiles baseline --out .eval/baseline
npm run eval -- --run --cases test/fixtures/eval/showcase.json --models claude-opus-5-5 --effort medium --repeat 2 --individual --with-hooks --profiles installed --out .eval/installed
npm run eval -- --summary .eval/baseline .eval/installed
```

`--with-hooks`를 주면 두 프로젝트에서 모두 Claude가 Skill, Read, Bash를 쓸 수 있습니다. hook과 skill은 이 도구를 설치한 프로젝트에서 실제로 동작합니다. `--with-hooks`를 빼면 실행 조건이 이 문서와 달라집니다. 이때 평가 스크립트는 `--profiles installed`로 만든 프로젝트에도 이 도구를 설치하지 않고 작성 지침만 넣습니다. Claude는 두 프로젝트에서 모두 아무 도구도 쓸 수 없습니다.
`--individual`을 주면 요청마다 새 세션을 엽니다. 이 옵션을 빼면 평가 스크립트는 요청을 모두 묶어 한 번에 보냅니다. `--effort`를 주지 않으면 `low`로 실행합니다. 결과는 `--out`에 준 경로에 저장합니다. 이미 결과가 있는 경로를 주면 실행하지 않고 멈춥니다. 이 저장소에서는 결과를 `.eval/` 아래에만 두고 커밋하지 않습니다.
`--cases`로 다른 평가 입력을 고를 수 있습니다. 이 옵션을 주지 않으면 평가 스크립트는 `cases.json`을 씁니다. 평가 입력은 [test/fixtures/eval/](../test/fixtures/eval/)에 있습니다. `calque.json`은 한국어로 옮기면 영어식 표현이 나오기 쉬운 영어 문장을 모은 입력입니다. 평가 스크립트는 요청마다 `mustNot`에 적은 표현이 답변에 나오면 제약 위반으로 셉니다.
