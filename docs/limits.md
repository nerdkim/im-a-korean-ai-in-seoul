# 제약

## skill과 작성 지침

- hook은 Claude가 skill을 불렀는지만 확인하고 skill에 적힌 순서를 모두 따랐는지는 확인하지 않습니다. 그래서 남은 문제는 검사기가 찾는 오류와 경고로만 드러납니다.
- 작성 지침과 skill에는 처음부터 한국어로 생각하라는 지시가 들어 있습니다. Claude가 실제로 어떤 언어로 생각했는지는 이 도구가 확인하지 못합니다. 그래서 지시가 통했는지는 사람이 답변을 읽고 판단해야 합니다.
- skill과 작성 지침에는 독자에게 필요한 내용만 고르고 공개하는 글에 내부 정보와 개인 정보를 넣지 말라는 지시가 들어 있습니다. 검사기는 글에 든 내용이 독자에게 필요한지, 공개해도 되는지 판단하지 못합니다. 검사기는 개발 서버 주소나 사람 이름을 오류로 잡지 않으므로 hook도 이런 글을 막지 않습니다.
- 작성 지침은 프로젝트 설정을 읽은 세션에만 적용됩니다. 다른 output-style을 고른 세션과 subagent에는 작성 지침이 들어가지 않습니다.
- hook은 subagent 프롬프트에는 skill을 요구하지 않습니다. 한글이 `writing-skill-min-hangul` 값보다 적게 든 글에도 요구하지 않습니다. 같은 요청에서 skill을 부르지 않았다는 이유로 두 번 막았는데도 Claude가 skill을 부르지 않으면 hook은 그 뒤로 이 이유로는 막지 않습니다.
- skill에는 CLAUDE.md 같은 프로젝트 지침, 기존 문서, 앞선 답변에 든 영어식 표현을 따라 쓰지 말라는 지시가 들어 있습니다. 하지만 이 도구는 그 글에 이미 들어 있는 표현을 고치지 않습니다. hook도 바뀐 문단에 새로 생긴 경고만 알립니다. 그래서 프로젝트 지침과 문서에 남은 영어식 표현은 사람이 `node .korean-style/scripts/check-korean.mjs --all` 결과를 보고 고쳐야 합니다.
- Codex나 Gemini CLI에서는 skill과 작성 지침, Claude Code hook이 동작하지 않습니다. 이 두 agent가 쓰는 글에는 Git의 `commit-msg` hook이 하는 커밋 메시지 검사만 적용됩니다.

## 검사기

- 검사기는 규칙 문서에 적힌 형태만 찾습니다. 서술어 하나에 정보를 몰아넣은 문장, 무엇을 가리키는지 흐린 지시어, 영어 문장과 낱말 단위로 맞아떨어지는 문장처럼 목록으로 정할 수 없는 문제는 잡지 못합니다. 항목 이름에 할 일을 몰아넣고 콜론 뒤에 누가 하는지만 쓴 목록도 잡지 못합니다. 이런 문제는 Claude가 skill을 따라 쓰면서 스스로 피해야 합니다. 이 도구 저장소에서는 커밋하기 전에 `korean-reviewer` agent로 한 번 더 검토합니다.
- 검사기는 말투마다 정해 둔 어미만 찾습니다. 합니다체 프로젝트에서는 `~세요`, `~어요` 같은 해요체 어미를 찾고 해요체 프로젝트에서는 `~니다`로 끝나는 어미를 찾습니다. 그래서 `~한다` 같은 해라체와 반말은 잡지 못합니다. 다만 답변에서는 `확인해라`, `확인해줘`처럼 `imperative-endings`에 적어 둔 명령 어미를 따로 잡습니다. 합니다체 프로젝트에서도 `~네요`, `~까요`, `~죠`처럼 정해 둔 목록에 없는 해요체 어미는 잡지 못합니다. `돼요`나 `봐요`처럼 어간과 합쳐진 해요체 어미도 일부 잡지 못합니다. 해요체 프로젝트에서는 `~해 주십시오`와 `~습니까`를 잡지 못합니다. 검사기가 잡지 못하는 어미는 Claude가 작성 지침과 skill을 따라 스스로 피해야 합니다.
- `셸`, `훅`, `스킬` 같은 음차는 기본 규칙에서 잡지 않습니다. 막으려면 `banned-transliteration`에 음차와 대신 쓸 영어를 넣습니다.
- 영어를 낱말 단위로 옮겨 만든 말은 규칙 문서에 적은 말만 잡습니다. 이 가운데 오류로 막는 말은 `calques`에 적은 말뿐입니다. 기본 규칙의 `calques`에는 `비멱등`, `미추적`, `반랙`, `전랙`, `응답 모양`, `바깥 접속`만 들어 있습니다. `코드 밖에서`, `어떤 모양으로`, run을 옮긴 `돌고 있`, test를 옮긴 `시험용`은 정상 문장에도 나올 수 있습니다. 그래서 기본 규칙에서는 이런 말을 `translationese-patterns`에 넣어 경고만 나오게 했습니다. 목록에 없는 말을 막으려면 `calques`에 그 말과 대신 쓸 표현을 넣습니다. `calques`에 적은 말은 코드 블록, 인라인 코드, 같은 줄에서 닫은 따옴표 안에 쓰면 잡지 않습니다. 앞에 한글이 붙어 있으면 `POST는비멱등이라`처럼 띄어 쓰지 않은 경우에도 다른 낱말의 일부로 보고 잡지 않습니다.
- 검사기는 항목을 새로 넣는 일을 `더하다`로 쓴 문장 가운데 목적어가 영어 낱말이거나 `object-verbs`에 적은 낱말인 문장만 경고로 알립니다. `저장소도 더할까요`처럼 목적어 뒤에 `을`, `를`, `은`, `는`이 아닌 조사를 쓴 문장은 잡지 못합니다. 영어 목적어는 `을`, `를`이 붙을 때만 잡습니다. 목록에 없는 낱말이 목적어인 문장과 `통합테스트를`처럼 목록의 낱말 앞에 한글을 붙여 쓴 문장도 잡지 못합니다. `사과 세 개에 두 개를 더하면`처럼 수를 합치는 문장도 목적어가 목록에 든 낱말이면 경고가 나옵니다. 목록에 든 낱말에 `은`, `는`을 붙여 주어로 쓴 문장에도 경고가 나올 수 있습니다. 지표를 `재다`로 쓴 문장도 같은 방식으로 `효과`, `성능`, `비용`처럼 목록에 든 낱말이 목적어일 때만 경고로 알립니다. hook은 경고 때문에 답변을 다시 쓰게 하지 않습니다. 그래서 답변에서는 Claude가 skill을 따라 스스로 고쳐 써야 합니다. Claude는 항목을 새로 넣는 일을 `추가하다`로 쓰고 지표를 구하는 일을 `측정하다`로 써야 합니다.
- 영어식 표현, 쉼표, 길이, 빈도 규칙은 경고로만 보고합니다. 경고가 나온 표현도 문맥에 맞으면 그대로 두어도 됩니다. CLI에 `--strict`를 붙이면 경고만 있어도 실패로 끝납니다.
- 말투와 표기 규칙 위반을 오류로 나눈 것은 프로젝트 정책입니다. 고유명사에 예외가 필요하면 규칙을 고칩니다.
- 같은 줄에서 닫은 큰따옴표, 한글이 든 작은따옴표, 낫표(`「」`, `『』`), 인라인 코드 안은 말투를 검사하지 않습니다. 코드 블록 안에서도 말투, 금지 문자(emoji 제외), 금지 호칭, 외래어 표기, 오타, 생성 표시는 오류로 잡습니다. 그래서 다른 말투로 쓴 글을 답변의 코드 블록에 옮기면 Stop hook이 다시 쓰라고 요구합니다.
- 문서에서 `<!-- korean-style-quote -->` 줄과 `<!-- /korean-style-quote -->` 줄 사이에 넣은 글은 검사하지 않습니다. 답변과 커밋 메시지에서는 이 사이도 검사합니다.
- 지원하는 확장자의 소스 파일에서는 주석만 검사합니다. 코드 안의 문자열과 지원하지 않는 확장자의 파일은 검사하지 않습니다. hook과 전체 검사는 프로젝트 밖 경로를 건너뜁니다.
- 전체 검사는 점(`.`)으로 시작하는 디렉터리와 제외 경로를 건너뜁니다.

## hook

- Stop hook은 답변이 화면에 나온 뒤에 실행되므로 이미 나온 답변을 되돌리지 못합니다. 그래서 첫 답변과 다시 쓴 답변이 함께 보입니다. 다시 쓴 답변은 검사하지 않으므로 고치지 못한 오류나 다시 쓰면서 생긴 오류는 그대로 남습니다.
- Claude Code가 마지막 답변을 넘겨 주면 Stop hook은 그 답변만 검사합니다. 이때 Claude가 도구를 부르는 사이에 쓴 진행 보고는 어느 hook도 검사하지 않으므로 진행 보고에 든 오류는 그대로 남습니다.
- 설치 스크립트가 `CLAUDE_CODE_THINKING_DISPLAY_UPDATES=0`을 넣으면 서버가 요약한 문장이 화면에 나오지 않을 뿐이고 Claude가 쓴 원래 진행 보고가 대신 나오지는 않습니다. 그래서 서버가 요약 대상으로 고른 진행 보고는 화면에 나오지 않습니다. 이 동작은 Claude Code 2.1.310에서 확인했습니다. 다른 버전에서는 환경 변수 이름이나 동작이 다를 수 있습니다.
- 사용자 설정에서 `showThinkingSummaries`를 켜면 Claude Code는 `CLAUDE_CODE_THINKING_DISPLAY_UPDATES` 값과 관계없이 서버에 사고 요약을 요청합니다. 이때 화면에 나오는 요약도 skill과 검사기를 거치지 않습니다.
- 구버전 Claude Code는 Stop hook에 마지막 답변을 넘기지 않습니다. 이때 hook은 대화 기록을 읽으므로 hook이 실행되는 시점까지 기록된 답변만 검사합니다.
- hook은 Write, Edit, MultiEdit, NotebookEdit 도구로 바꾼 문단에서 `review-rules`에 든 규칙의 경고만 Claude에게 알립니다. 같은 규칙에 걸린 같은 표현이 바뀌기 전 문단에도 있으면 알리지 않습니다. 그래서 이미 있던 표현을 같은 문단에 한 번 더 써도 알리지 않습니다. NotebookEdit 도구로 셀을 고칠 때는 바뀌기 전 셀과 비교하지 않으므로 원래 있던 경고도 알립니다.
- hook은 shell 명령이 파일에 쓰는 경우 가운데 redirection(`>`, `>>`)과 `tee`, `sed -i`, `perl -i`만 알아봅니다. 이 검사는 보안 장치가 아닙니다. 명령으로 실행한 프로그램이 직접 쓰는 파일은 찾아내지 못합니다.
- hook은 `gh pr`과 `gh issue` 명령의 `--title`, `--body`, `--subject`, `-t`, `-b` 값과 `-F -`나 `--body-file -`로 넘긴 heredoc 본문만 검사합니다. 파이프로 넘긴 본문은 읽지 못합니다. `--body-file`로 넘긴 파일과 웹 화면에서 쓴 글은 검사하지 않습니다.
- hook은 shell 문법을 다 해석하지는 못합니다. 변수에 담아 넘긴 메시지나 `$(...)`로 다른 명령의 출력을 넘긴 메시지는 읽지 못합니다. 다만 Claude가 여러 줄 메시지에 쓰는 `"$(cat <<'EOF' ... EOF)"` 형태에서는 heredoc 본문을 읽습니다. 커밋 메시지는 Git의 `commit-msg` hook이 다시 검사합니다.
- hook을 실행하다 예외가 나면 작업은 계속됩니다. 규칙 문서가 맞는지는 `doctor`와 `gate`로, hook이 연결되었는지는 `doctor`로 확인합니다.
- 일반 편집기로 파일을 고치면 Claude Code hook은 실행되지 않습니다.

## 설정과 설치

- 설치 스크립트는 설정 파일 가운데 프로젝트 설정(`.claude/settings.json`)만 바꿉니다. 로컬 설정, 조직 정책, 세션 옵션은 프로젝트 설정보다 우선합니다. 그래서 이 가운데 한 곳에서 다른 output-style을 고르거나 hook을 끄거나 `attribution` 값이나 `env`의 `CLAUDE_CODE_THINKING_DISPLAY_UPDATES` 값을 바꾸면 이 도구의 설정이 적용되지 않습니다.
- doctor는 프로젝트 설정 파일과 로컬 설정 파일만 확인합니다. 세션에 실제로 적용된 설정은 Claude Code의 `/status`로 확인합니다.
- 직접 고친 규칙은 다시 설치해도 바뀌지 않으므로 새로 생긴 `review-rules` 키도 들어가지 않습니다. 이 경우 doctor가 주의 항목으로 표시합니다. `calques` 키, `object-verbs` 키, `더하다`를 잡는 `literal-verbs` 항목도 들어가지 않습니다. `calques`와 `translationese-patterns`에 새로 넣은 `반랙`, `코드 밖에서` 같은 항목도 들어가지 않습니다. doctor는 이런 항목이 빠졌다고 알리지 않습니다. 새 기본 규칙으로 바꾸려면 `--force`를 붙여 다시 설치합니다. 그런 다음 `.korean-style/rules.backup-*.md`에 백업된 기존 규칙에서 필요한 내용을 직접 옮겨 옵니다.
- 설치한 프로젝트의 gate는 이 도구 저장소의 테스트를 실행하지 않고 자체 검사, 규칙 문서 검사, 전체 파일 검사만 합니다.
- 자체 검사는 이 도구와 함께 배포한 기본 규칙으로 검사기를 확인하므로 사용자가 규칙 값을 바꿔도 실패하지 않습니다. 실제 답변과 문서는 프로젝트 규칙으로 검사합니다.

## 평가

- 이 도구 저장소에서 실제 모델로 하는 평가는 정해 둔 요청으로 합니다. 같은 요청이어도 모델, effort, 캐시, 서버 상태에 따라 답변과 실행 시간이 달라집니다.
- Claude Code는 실행할 때마다 서버에서 기능 설정을 받아 오고 이 설정에 따라 시스템 프롬프트가 바뀔 수 있습니다. 평가 도중 시스템 프롬프트가 바뀌면 같은 요청을 다시 보내도 앞서 캐시에 저장한 입력을 읽지 못해 비용이 줄지 않습니다. `npm run eval -- --summary`는 같은 요청을 다시 보낸 결과가 있으면 처음 보낸 요청과 다시 보낸 요청의 비용을 나눠 보여 줍니다. 평가 도중 시스템 프롬프트가 바뀌면 이 두 비용의 차이가 작게 나오므로 `--summary`가 보여 주는 표에서 알아챌 수 있습니다.
- 이 도구 저장소의 README에서 설치 전후 비교에 쓴 요청 열두 가지 가운데 다섯 가지는 skill 예문과 같은 낱말이나 문장을 씁니다. README 표에서 검사기로 센 해요체 어미, 금지 문자, 생성 표시는 이 예문이 다루는 문제가 아닙니다. 사람이 답변을 읽고 센 머리말, 덧붙인 말, 요청에 없는 내용은 skill 예문과 겹치지 않는 요청에서도 이 도구를 설치한 프로젝트의 답변에서 더 적게 나왔습니다. 하지만 어떤 낱말을 골랐는지는 skill 예문과 겹치는 요청과 겹치지 않는 요청으로 나눠 비교하지 못했습니다. 그래서 낱말 선택에서 보인 차이는 skill 예문 때문일 수 있습니다. 나눠 센 결과는 이 도구 저장소의 `docs/examples.md`에 있습니다.
- `native-verb.json`의 요청을 보낸 평가에서는 지시를 넣기 전에도 Claude가 `더하다`와 `재다`를 쓰지 않았습니다. 그래서 이 평가로는 skill에 넣은 두 지시의 효과를 확인하지 못했습니다. 이 도구를 설치한 세션의 대화 기록에서는 `더하다`와 `재다`가 긴 작업 중 진행 보고와 작업 보고에 주로 나왔습니다.
- `npm run eval -- --summary`는 검사기와 기록으로 셀 수 있는 항목만 셉니다. 머리말, 묻지 않은 제안, 요청에 없는 내용처럼 사람이 읽고 판단해야 하는 항목은 세지 않습니다.
